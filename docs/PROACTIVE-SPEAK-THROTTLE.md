# 主动搭话的节流曲线（迁移自 dsh-speak-up v0.2.3，2026-10-26）

> **本文档是什么**：一份「如果要让 agent 自己找话题说话，该按什么节奏」的实现规范。
> **本文档不是什么**：不是已启用的功能。本机当前**没有**主动搭话驱动器在跑。
>
> **为什么只留规范不建驱动器**：
> 1. 主动搭话的实现形态是「往会话里注入一条 role=user 的消息并驱动一轮」——
>    这与 feiyu-mood 的 systemPrompt 注入是不同性质的侵入（后者不产生对话回合）
> 2. 每次触发都有一次模型调用成本，而「AI 自己找话题」这个需求在本机**尚未被验证过**
> 3. 本机已有 4 个自动化任务，全是确定性记忆维护；突然加一个概率型主动说话属于行为改变，
>    应该显式决定，而不是顺手装上
> 4. 真要启用时，用 `automation_task_create` + 下面的判定式建一个任务即可，成本极低
>
> 源插件：`Yuuyuko-uu/dsh-speak-up`（未声明许可）。本项目**未安装它**，只取机制。

---

## 一、原插件的真实参数（源码实测，非 README 转述）

| 参数 | 值 | 说明 |
|---|---|---|
| 掷骰间隔 | 30 分钟 | `ctx.interval` 定时，改配置下一轮自动换表 |
| 峰时命中线 | 20 | 09:00–12:00、14:00–18:00；**周末全天按谷时** |
| 谷时命中线 | 60 | 其余时间 |
| 连续未中加成 | +10 / 次 | 上限 +40 |
| 近阈值窗口 | 20 分钟内 → 因子 **0.15** | 「刚说过话」时几乎不再开口 |
| 远阈值窗口 | ≥360 分钟 → 因子 **1.5** | 「很久没说了」时更容易开口 |
| 安静时段 | 01:00–08:00 | 支持跨午夜；起==止视为不启用 |
| 冷却 | 20 分钟 | **只在真发成功后**设置 |
| 每日上限 | **没有** | 只有节流，没有硬上限 |

## 二、判定式（唯一权威口径）

```
命中线 = min(100, 档位命中线 × 时机因子 + min(40, 连续未中 × 10))
掷 0–100 的随机数
  掷值 ≥ 命中线 → 没中：连续未中 += 1（下次更容易中）
  掷值 <  命中线 → 中：整轮发话，连续未中清零，冷却 20 分钟
```

**两条容易搞反的语义**：

1. **「距上次说话」指的是用户上次 `user/message`，不是它自己上次开口。**
   原插件从 `sessionController.inspect` 翻已落盘历史取这个时间，并**排除
   `source.kind === 'speak-up'` 的消息**——否则它会把自己上次的独白当成「刚聊过」，
   越说越不想说。
2. **掷值 ≥ 线 = 没中**（不是「掷中」）。所以 `连续未中` 越大、命中线越高，
   中奖概率反而越高——这是一条**保底机制**，不是惩罚。

## 三、原插件里不该一起迁的东西

| 原设计 | 为什么不迁 |
|---|---|
| **没有每日上限** | 只有节流没有硬闸门。一旦时机因子+加成叠加到命中线上限 100，理论上可以一天说很多次。迁的时候应当加一个 `每日最多 N 次` 的硬闸门 |
| **连续未中只加频、不降权** | 它没有「说了没人理 → 下次更少说」的反馈环。真实产品需要，否则会变成单向递增的骚扰倾向 |
| **计数只在内存、重启归零** | 重启后「连续未中」清零 = 重启当天更容易一上来就开口。迁的时候必须持久化 |
| **`/new-session` 会真建会话** | 它有一条路由能直接创建新会话。这类副作用不该暴露给概率机制 |

## 四、如果要启用，怎么建（三步）

**第 1 步**：先决定「在哪个会话里说」。必须在**你实际会看**的会话里，否则说了没人看见。
注意 `automation_task_create` 是把任务绑到项目的「⚙ 自动化任务」专用会话上——
如果希望话出现在主会话，需要在 prompt 里显式要求它用 `de_session` 投递，或者接受
「话出现在自动化会话里、你去那里看」。

**第 2 步**：建一个低频任务（间隔不小于 30 分钟），prompt 形态：

```
你是主动搭话的判定器。按下面的顺序做，**任何一步不满足就静默结束，不要说任何话**。

1. 现在是几点？如果在 01:00–08:00，结束。
2. 距离用户最后一条 user 消息多久了？
   <20 分钟 → 因子 0.15；20–360 分钟 → 因子 1.0；>360 分钟 → 因子 1.5
3. 档位线：工作日 09–12 / 14–18 用 20，其余（含周末全天）用 60。
4. 读 <状态文件> 里的 consecutiveMisses，命中线 = min(100, 档位线 × 因子 + min(40, consecutiveMisses × 10))。
5. 掷一个 0–100 的随机数，记作 R。
6. R ≥ 命中线 → consecutiveMisses += 1，写回状态文件，**结束，不说话**。
7. R < 命中线 → 检查今天已说次数，≥ 3 次就结束。
   否则：写回 consecutiveMisses = 0 与「今天已说 +1」，然后说一句不超过两句话的、
   与当前工作上下文有关的话。不要说「我正在检查是否需要说话」这类元叙述。
```

**第 3 步**：状态文件放 `~/.dsh-beta/proactive-speak-state.json`，字段
`{ consecutiveMisses, saidToday, dateISO }`。**必须持久化**（理由见上表）。

## 五、验收判据（建完之后）

- **不能只验证「它说过话」**，必须同时验证「它在该沉默的时候沉默了」：
  把状态文件的 `consecutiveMisses` 设成 0、把时间调成刚聊过 5 分钟，
  此时命中线 = 60 × 0.15 = 9，10 次触发里大约 1 次会说话 —— 若每次都说话，说明因子没生效。
- 把 `dateISO` 改成昨天，验证 `saidToday` 会归零而不是累加。
- 观察 24 小时，统计「触发次数 / 实际说话次数 / 用户回应次数」三个数。
  **只看前两个看不出它烦不烦人，第三个才是真正的判据。**
